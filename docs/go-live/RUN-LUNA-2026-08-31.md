### História 1 — CI do Rust para de quebrar

Fato: `cli/benchmark-probe/Cargo.toml` declara `argos-opt` por path para fora
do repositório, e `cli/benchmark-probe/AGENTS.md` diz "do not vendored-copy it".
O runner do GitHub não tem esse diretório, então `cargo test --workspace` morre
antes de compilar qualquer coisa. O package de `cli/canirunit` chama-se
`canirunit`.

Mudança, arquivo `.github/workflows/ci.yml`, no job `rust-cli`:
trocar a linha que roda `cargo test --workspace` por uma que roda
`cargo test -p canirunit`, e acrescentar logo acima um comentário de 2 linhas
dizendo que `benchmark-probe` depende de um path dep local (`argos-opt`, nome
ainda não definido) e que se volta a `--workspace` quando essa dependência
virar git/registry dep.

NÃO: não remova o job, não mexa no job `python` (está verde), não toque em
nenhum `Cargo.toml`, não crie o diretório argos-opt.

### História 2 — a home para de liderar com n=1

Fato: `apps/web-next/app/page.tsx` tem uma função `build()` que monta o índice
de respostas e, para cada chave, ordena por velocidade decrescente
(`(b.metric?.value ?? b.tokS) - (a.metric?.value ?? a.tokS)`) e corta em
`ANSWER_LIMIT`. Cada entrada já carrega o campo `basis`, com valor `measured`
ou `reported`. Hoje o número-herói do default é uma célula `reported` com n=1.

Mudança, mesmo arquivo, apenas o comparator daquele sort: ordenar primeiro por
posto de basis (`measured` antes de `reported`) e, dentro do mesmo basis,
por velocidade decrescente como já é hoje. O corte em `ANSWER_LIMIT` continua
DEPOIS do sort. Como o sort vive dentro de `build()`, que serve tanto `index`
quanto `indexAny`, a mudança é num lugar só — não duplique.

Acrescente um comentário de 1-2 linhas explicando por que measured ganha
(escada de honestidade: o herói da home é endosso implícito da casa).

NÃO: não mude o client (`home-client.tsx`), não mude `ANSWER_LIMIT`, não filtre
nem esconda células `reported` — elas continuam na lista, só perdem a primeira
posição para uma measured quando existir.

### História 3 — página das âncoras de nuvem

Problema: as runs medidas em GPU de nuvem são o melhor argumento de
credibilidade do produto e hoje só aparecem indiretamente, porque rigs de nuvem
ficam fora do top-24 do seletor da home.

As rigs de nuvem são exatamente as duas cujo `label` termina em `(modal)`, em
`apps/web-next/public/data/derived/hardware.json`: `l4-24gb` ("L4 24GB (modal)",
bandwidthGBs 300) e `a10-24gb` ("A10 24GB (modal)", bandwidthGBs 600). NÃO existe
campo booleano de nuvem — selecione pelo sufixo do label, e deixe isso explícito
num comentário, porque é um marcador frágil.

Existem exatamente 5 células nessas rigs, todas measured (n≥3):

    a10-24gb  Llama 3.1 8B Instruct GGUF      n=3  75.83 tok/s  4-bit  chat
    l4-24gb   Llama 3.1 8B Instruct GGUF      n=3  44.76 tok/s  4-bit  chat
    l4-24gb   Qwen2.5 Coder 7B Instruct GGUF  n=3  47.24 tok/s  4-bit  code
    l4-24gb   sd-turbo                        n=5  (métrica de imagem)  image
    l4-24gb   Whisper Large v3                n=5  (métrica de áudio)   audio

Crie a rota `apps/web-next/app/cloud-anchors/page.tsx`: Server Component SSG,
sem client component, sem estado. Ela lê o pool derivado pelos helpers que já
existem em `apps/web-next/lib/engine.ts` (`loadDerived`, `basisOf`, e
`metricOf` para as células cuja métrica não é tok/s) — não releia JSON na mão
nem duplique lógica de basis.

Conteúdo, nesta ordem:
1. Kicker + título curto + um parágrafo dizendo o que a página é: runs medidas
   em GPU alugada, fora do hardware da comunidade, para ancorar a escala.
2. Uma linha por célula, mono, com: modelo, rig, valor + unidade, basis e n.
   Toda linha declara basis e n — sem exceção.
3. Um bloco curto sobre a comparação A10 × L4: MESMO modelo, MESMA quantização
   4-bit, n=3 dos dois lados; decode foi de 44.76 para 75.83 tok/s, ou seja
   **1.69×**, enquanto a banda de memória vai de 300 para 600 GB/s, ou seja
   **2.0×**.

   REGRA DURA DE HONESTIDADE: 1.69 não é 2.0. É PROIBIDO escrever que a razão
   "bate com", "confirma" ou "é igual à" razão de banda. O texto correto diz
   que o ganho é sub-linear em relação à banda — consistente com decode
   limitado por memória, sem ser proporcional a ela. Não invente explicação
   causal além disso.
