## Verdict: FAIL

Byte parity holds for the chain itself everywhere (steps 2, 3, 4 zero diffs in
both credential states; step 5 post-gate lines identical). The spec's oracle
requires "zero diffs in 2–5"; step 5 also requires **both sides to emit a WARN
mentioning E5-M2** on a stamped FANTASMA ref — the shell path emits none (its
`capture_output=True` swallows the resolver's stderr on success). Only the
kernel warns. The bug is on the shell side of the shadow pair; the kernel side
is correct and now pinned. A second bug (pre-existing on main, found by the
battery oracle) is the L3 proptest counterexample.

## Findings

1. **bug** (laws touched: L2 / E5-M2 mechanism, shell side) — The shell path
   swallows the stamped catalog's dead-id WARN: `run-with-fallback.sh`'s
   CHAIN_META python runs `lib-oracfit-mode-loader.py` with
   `capture_output=True` and only re-emits the inner stderr on failure, so a
   `FANTASMA` ref is skipped **silently** on the shell side. The kernel emits
   the E5-M2 WARN (step 5 parity broken: both skip, only one warns). Repro
   under step 5; kernel-side behavior pinned by vector
   `T08_dead_keyless_leg_skipped`. T08 does not modify the shell — reported.
2. **bug** (laws touched: L3, mechanism `l3_cheap_order`) — Pre-existing on
   main (proven by replay on a clean tree): L3's "pure function of the
   catalog content / byte-deterministic" claim is falsified by two catalog
   models with identical sort keys (same ref `"t"`, both keyed, context null,
   different provider): Rust's stable `sort_by_key` keeps input order, so
   reversing the input reverses the tie. The Python reference sorts with the
   same stable tiebreak, so shell↔kernel parity holds — the law statement is
   stronger than both implementations. Counterexample pinned in
   `tests/laws.proptest-regressions` (minimal input:
   `[{ref:"t", provider:Some("opencode"), keyless:false, context_length:None},
   {ref:"t", provider:None, keyless:false, context_length:None}]`).
3. **note** (laws touched: L1, adjacent) — Registry `id_status` is
   string-or-null in the wild: with `"id_status": null` on the matched model
   or a fallback target, the shell's direct-path python crashes
   (`TypeError: can only concatenate str (not "NoneType") to str`,
   `MODEL=gpt-6-astra REG=/tmp/t08/registry-null-status.json ...`), while the
   kernel normalizes null → `""` and resolves fine
   (`gpt-6-astra^_^_cheaper-inference^_1$`). Kernel is the safe side; latent
   shell crash only, not reachable from today's `model-registry.json`.
